# Database changes

Supabase PostgreSQL is the configured database target. On 8 November 2026, migrations 001–005 were applied to the configured hosted development database through the session pooler with certificate and hostname verification enabled. A repeat run applied zero migrations. The restarted local backend returned readiness HTTP 200 and the public catalogue. Subsequent connected tests created clearly fictional accounts, family profiles, organizations, activities and requests. No real family/contact records or payments were used.

Run `npm run db:migrate` against the intended development database. The runner sorts versioned SQL files, serializes migration runs with a PostgreSQL transaction advisory lock, stores SHA-256 checksums in `app.schema_migrations`, and rejects changed applied files. Schema changes and ledger entries commit together. It safely adopts the original manually applied 001 schema because that migration is idempotent.

- `001_platform.sql`: original private domain schema.
- `002_provider_memberships.sql`: organization membership and existing-owner backfill.
- `003_minimal_child_profiles.sql`: optional surname and age-or-birth-date profiles.
- `004_saved_activities.sql`: account-scoped saved activities.
- `005_paginated_list_indexes.sql`: stable list/sort indexes for catalogue, families, providers, sessions, bookings, saves and operational history.
- `006_capabilities_and_branches.sql`: explicit platform capability grants, provider branches/roles, assigned booking staff, tenant-consistent foreign keys, shared permission predicates and permission-change audit triggers. Backfills a default branch and existing listing references; grants no new staff/platform permissions. See [rollout and access details](../docs/PERMISSIONS_FOUNDATION.md).
- `007_booking_deadlines.sql`: finite payment-review deadline, payment-exception and deduplicated reminder records. Existing `PAYMENT_CHECKING` bookings receive a bounded deadline based on their first payment submission and session cutoff; accepted bookings receive a payment-window start from audit history where available. Rehearse these backfills with synthetic staging data before applying them to any live environment.
- `008_public_contact.sql`: private public-contact submission queue and status index. Adds no grants to browser roles and changes no existing records. Applied to the configured owner-designated staging database on 20 November 2026; one synthetic guest message was submitted and verified by a read-only query.
- `009_contact_email_delivery.sql`: additive delivery state and per-attempt history for new contact enquiries. Applied to the configured owner-designated staging database on 20 November 2026. Pre-existing submissions remain `not_queued`; one new synthetic browser submission was SMTP-accepted on its first attempt, and a matching message was found in the configured mailbox's inbox over authenticated IMAP. The backend private environment now enables contact SMTP; ongoing dispatch still requires a supervised worker in the deployment.
- `010_contact_acknowledgments.sql`: additive private queue and attempt history for optional customer thank-you receipts. Applied to the configured owner-designated staging database on 20 November 2026. No existing submissions were backfilled and no customer receipt was sent; `CONTACT_ACK_ENABLED` remains off pending public-form abuse controls.

Do not edit an applied migration; add another version. Do not create production tables from startup code. Preserve booking/payment/refund history and tenant ownership. Keep credentials out of Git and use isolated development/staging/production projects. The advisory-lock path is executed in embedded tests, but a real hosted concurrent last-place acceptance case also passed; broader staging concurrency/load verification remains required.

Do not import real contacts or children into this public repository. Contact import data belongs in restricted application storage, not migration fixtures.
